- Base: `2026-10-06-raspios-trixie-arm64-lite` (Debian trixie, Linux 6.18, arm64)
- Target: Raspberry Pi 5 (BCM2712), 8 GB RAM recommended
- Launcher: PiVista TV launcher 0.3.0
- Image: `pivista-tv-0.3.0-pi5-arm64.img.xz` (1,230,380,528 bytes / 1.23 GB compressed)
- SHA-256: `acc6240773197036a8337948aa355064e3187e233ffd9b2174339b3e57098fb5`
- Host tests: 69 host Python tests, 7 launcher/Qt cases, 29 offscreen renders, 51/51 image checks

## What's new

- **Signed launcher updates.** Settings → Updates can check the official GitHub
  repository, show release notes and size, download, verify, install and roll
  back a launcher application update. The manifest is signed with an Ed25519
  key installed in the image; the archive is checked against the SHA-256 in the
  signed manifest. No script from GitHub is executed.
- **Separate launcher and image versions.** Settings shows both. A launcher
  update does not pretend to update the OS image.
- **Safe install and rollback.** The previous binary, QML, catalog and version
  file are copied to a root-owned rollback directory before the swap. A failed
  install restores them. User settings, favourites, browser profiles, web
  shortcuts and NetworkManager connections are not touched.
- **Bounded rollback storage.** Only the immediately previous launcher is kept;
  older rollback trees are pruned after a successful update.
- **Prerelease is opt-in.** Stable releases only by default.
- **Recovery state.** An interrupted download/install is reported as failed
  rather than leaving a permanent spinner; active jobs are reset on daemon
  restart.
- **Periodic check.** The launcher performs a read-only check at startup and
  every six hours. It never auto-downloads or auto-installs, and it does not
  interrupt a playing video.
- **OS package controls remain separate.** The existing apt check/install path
  is still available. It has no A/B rollback.

The launcher archive is deterministic and signed. Its manifest declares
`min_version = 0.3.0` and `min_system = 0.3.0`; it never replaces the OS image.
Future launcher updates use this same channel. The privileged updater daemon is
image content, so changes to it require an image release rather than a launcher
update.

## Upgrading a 0.1.0 card

A **0.1.0 device cannot apply this update in place**. That image contains
neither the privileged updater actions nor the update public key, so there is no
safe bootstrap path from its unprivileged launcher.

One-time migration:

1. Keep the 0.1.0 image as the known-good fallback.
2. Download and verify the 0.3.0 image.
3. Optionally copy `/home/pivista/.config/` and `/var/lib/pivista/` off the card.
4. Flash 0.3.0, complete first boot, restore those directories if wanted.
5. From 0.3.0 onward, use Settings → Updates for launcher updates.

## Flash

```bash
sha256sum -c pivista-tv-0.3.0-pi5-arm64.img.xz.sha256
xz -dc pivista-tv-0.3.0-pi5-arm64.img.xz | \
  sudo dd of=/dev/sdX bs=4M status=progress conv=fsync
```

Or use Raspberry Pi Imager / balenaEtcher and select the `.img.xz` directly. Do
not apply Imager OS customisation (hostname, user, SSH, Wi-Fi); PiVista runs its
own first boot. The image keeps the Raspberry Pi OS layout: a 512 MB FAT32 boot
partition and an ext4 root partition that grows on first boot.

## Honest status

The Linux TV interface, application library, browser shortcuts, settings and the
signed launcher update channel are implemented and covered by host tests. The
image was sealed and structurally validated; its launcher was executed from the
sealed filesystem under qemu-user and the UI was rendered from it. The sealed
image's updater module was also compared byte-for-byte with the source.

**It was not booted on a physical Raspberry Pi 5.** The Pi was unreachable during
this build, so first boot, HDMI output/audio, Wi-Fi, remote input, GPU
performance and a real network update remain hardware tests. Protected 1080p
playback from Netflix/Disney+ is **not verified**; Android compatibility is
**not shipped**.

## Known limitations

- No physical Pi 5 boot or update test in this release.
- No full-image A/B update and no automatic package rollback. RAUC/`tryboot` was
  investigated, but the current single-slot layout cannot be updated safely
  in place; see `docs/updates.md`.
- No in-place upgrade from 0.1.0; one-time reflash is required.
- The updater daemon, trust key and service unit are image content and are not
  self-updating.
- Prereleases are identified by GitHub's release flag; a stable-looking tag
  without that flag is treated as stable.
- The release notes preview in Settings is intentionally short and capped.
- Widevine L1, Google Play services, Bluetooth pairing UI and HDMI-CEC are not
  provided or not verified.

## Recovery

See `docs/recovery.md` for the launcher rollback procedure, the physical emergency
shell and the reflash path. The launcher update backup lives under
`/var/lib/pivista/updates/rollback/`; do not delete it while diagnosing a failed
update. System package failures still require reflashing.
